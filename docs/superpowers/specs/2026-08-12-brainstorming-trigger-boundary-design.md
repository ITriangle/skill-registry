# Brainstorming Skill 触发边界调整设计

## 背景

当前 `vendor/obra-custom/brainstorming` 将触发范围定义为“任何创造性工作”，并在正文中要求待办清单、单函数工具和配置修改等简单任务也必须走完整设计流程。这会让目标、范围和验收标准已经明确的机械性修改产生不必要的澄清、方案比较、规格和计划步骤。

## 目标

将该 Skill 限定为：

- 开放式功能设计；
- 重大行为变更；
- 关键需求、方案或验收标准尚未明确，确实需要先探索再实施的任务。

同时明确：目标和验收标准已经清楚、无需设计决策的机械性修改不触发该 Skill。

## 修改范围

### 1. 触发描述

修改 `SKILL.md` 的 `description`，同时说明应触发和不应触发的场景。应触发场景包括新功能方向探索、多个可行方案之间的产品或技术决策、跨组件或对外行为的重大改变。明确排除格式转换、文案润色、错别字修复、直接替换、小范围配置和已有批准方案的执行。

### 2. 硬门禁

保留“设计批准前不得实现”的门禁，但只对已经符合触发条件的任务生效。删除“无论多么简单都适用”的绝对表述，避免正文重新扩大触发范围。

### 3. 简单任务边界

将“这太简单，不需要设计”的反模式改为“先判断是否存在真实设计决策”：

- 如果存在尚未决定的用户体验、架构、接口、数据流、范围或显著权衡，则进入 brainstorming；
- 如果用户已经给出明确变更和验收标准，执行只需机械编辑或局部实现，则直接执行；
- 任务规模小不自动排除 brainstorming，任务涉及代码也不自动触发 brainstorming，判断依据是设计不确定性和行为影响。

### 4. 流程弹性

完整流程继续适用于开放式或重大设计任务。对于范围已经基本明确、仅剩一个小型设计决策的任务，允许使用简化流程：核对上下文、提出必要问题、给出简短设计并取得批准，不强制为机械修改生成独立规格和提交。

### 5. 中文同步

同步修改 `locales/zh-CN/vendor/obra-custom/brainstorming/SKILL.md`，保持触发语义、门禁和排除项一致；随后更新翻译戳并执行翻译审计。

## 不修改的内容

- Skill 名称和目录不变；
- 可视化 Companion 的使用规则不变；
- 对真正开放式功能设计的逐步澄清、方案比较和用户批准机制不变；
- 不修改 `vendor/obra/brainstorming` 变体；
- 不改变技能分组和依赖关系。

## 验收标准

1. 下列请求不应自动触发：
   - “把这段 JSON 示例改成非技术人员可读的 Markdown 表格。”
   - “修正文档里的错别字并统一标题格式。”
   - “按已经批准的规格实现这个字段改名。”
2. 下列请求仍应触发：
   - “设计一个新的客户 onboarding 流程，我还没想清楚步骤。”
   - “我们要重构权限系统，有 RBAC 和 ABAC 两个方向，帮我确定方案。”
   - “给现有产品增加离线模式，先梳理用户体验和数据同步策略。”
3. 英文真源与中文说明语义一致。
4. `bin/regctl translation-audit` 通过。
5. Skill 文本不再同时出现“仅重大/开放式任务触发”和“所有简单任务都必须触发”的矛盾规则。

## 验证方式

- 人工检查触发描述、硬门禁和简单任务边界的一致性；
- 使用上述正反例进行触发边界检查；
- 运行 `bin/regctl translation-stamp vendor/obra-custom/brainstorming`；
- 运行 `bin/regctl translation-audit`；
- 运行 `git diff --check`。
